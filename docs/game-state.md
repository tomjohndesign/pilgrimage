# Game state and the save document

Pilgrimage keeps one description of a world that the running game, the
browser's save slot and, later, player accounts and agent tools all share. This
page explains what that document holds, where it lives, and how it is meant to
grow.

## One document, three consumers

`lib/game/save/schema.ts` defines the `GameSave` document with zod. Every field
is named for what it means to a player and carries a description, so the same
schema serves as:

- the autosave written to `localStorage` under `pilgrimage.game.v1`;
- the payload a cloud save will upload once accounts exist;
- the contract for tools that let an agent read or change a world on the
  player's behalf (a WebMCP surface is planned).

The map itself is never stored. Land is a pure function of the seed and the
world settings, so the document records those inputs and only what was done on
top of them. A save is tens of kilobytes on a default map, not megabytes.

## Sections

| Section      | Holds                                                                                  | Rebuilt on load from                     |
| ------------ | -------------------------------------------------------------------------------------- | ---------------------------------------- |
| `world`      | Seed plus every generation input: size, forest, glades, water, elevation, traffic.     | Regenerated by `generateMap`.            |
| `settlement` | Claimed buildings, coffer, cumulative credits, admission fee, structures in order.     | Ground levelling is replayed per structure. |
| `simulation` | Day count, economy totals, relic reputation, felled trees, timber and food stores, each person's lasting state, brothers who joined. | Errands, routes, seats and carts are re-planned. |
| `camera`     | Focus point, rotation and zoom.                                                        | Applied after the opening reveal.        |
| `playback`   | Paused flag and simulation speed.                                                      | Applied as the world opens.              |

People are saved as who they are, not what they were doing. Attributes, purse,
job, home and place on the road survive; a traveler rejoins the road where they
were and a resident wakes idle on the spot and asks their workplace for a task.
That keeps the format independent of the simulation's internal routing state,
which is large, reference-heavy and changes often. Wildlife, worn footpaths
and the monks' own routine are rebuilt from the seed.

## Where state lives at runtime

- **World identity** is React state in `components/game/game-shell.tsx`: the
  seed and `MapSettings`, which is `WorldSettings` plus `DisplaySettings` from
  `lib/game/save/settings.ts`.
- **Settlement** is React state in `hooks/use-settlement.ts`.
- **Simulation** is the mutable `SimState` from `lib/game/sim.ts`, published
  through `simRegistry` for readers outside the canvas.
- **Camera and playback** are zustand stores.

`captureGame` in `lib/game/save/capture.ts` assembles the document from those
pieces; `restoreSettlement` and `restoreSimulation` apply it back.

## URL and storage

The root `/` is the landing page: pick a seed and size for a new world, or
continue the saved one. `/play` is always the game. Its URL names a world and
nothing else: `?seed=` and `size=` always, plus whichever generation inputs
differ from their defaults. A bare `/play` resumes the browser's save, or rolls
a new world when there is none. A link that names a seed or any input resumes
only when they all agree with the save; otherwise it is a request for a
different land, and the next autosave replaces the slot.

Display tuning (walk speed, sprite sizes, visibility, road look) is a
preference of the device, stored separately under `pilgrimage.display.v1` and
kept across new maps. Older links that carry display parameters are still read
but never written back.

A resumed world opens where the player left off,
at the same zoom and rotation, with a picture of the last view standing in
for the terrain while it regenerates; the reveal then spreads from there. The
landing page and the opening on the founding church are for a fresh start.

That picture is presentation cache, not part of the document. Each autosave
also keeps a crop of the game's own world buffer around the camera focus under
`pilgrimage.view.v1` (`lib/game/save/view.ts`), cut into a disc of whole tiles
and tagged with the world and camera pose it was taken at. The cut follows the
world pass's object IDs: a tree or building shows entire when the tile it
stands on is inside the disc and not at all when it is not, and bare ground
follows the tile under it. The play page inlines a script that paints it at
the saved zoom while the HTML is still parsing, so the middle of the screen
shows exactly what the reveal will uncover, from the first frame. A save with
any other pose ignores it.

Autosave runs every five seconds while a world is open and whenever the tab is
hidden or the page goes away. One slot per browser for now; accounts add named
slots on top of the same document.

## Versioning

`SAVE_VERSION` guards the shape. When a field changes, bump the version and
migrate older documents inside `parseGameSave` rather than rejecting them.
Unknown fields are dropped; records that no longer fit the world (a building
that is gone, a tree index past the end) are skipped rather than failing the
load.

## Towards agent tools

The document is the read model. Changes should go through the same functions
the HUD uses, so an agent can never put a world into a state the player could
not reach: `purchaseStructure` for buildings, the seed and settings setters for
new land, the balance store for tuning. A future tool layer would expose
roughly:

- `describe_world`: the current `GameSave` (or a summary of it);
- `place_structure(buildType, x, z, rotation)`: validated placement;
- `set_admission(fee)`, `set_playback(paused, speed)`;
- `new_world(seed, settings)`: regenerate;
- `save` / `load`: the browser slot, later account slots.

Because every field is described in the schema, the tool descriptions can be
generated from it rather than written twice.
